# Diagnostics Guide

The repository has two diagnostic layers: a fast local layer for TypeScript and ESLint, and a
complete free SonarQube Community Build layer for languages and rules that those tools do not
cover. The aggregate command runs both and never treats a missing analyzer as a clean result.

## Requirements

- Node.js 22 or newer and npm 10 or newer
- Docker Desktop with Docker Compose for SonarQube diagnostics
- The workspace-recommended VS Code ESLint and SonarQube for IDE extensions for editor feedback

The local server uses the pinned `sonarqube:26.11.0.134175-community` image and its embedded H2
database. H2 is appropriate for this disposable developer service, not for a shared or production
SonarQube installation. Shared installations must follow SonarSource's supported external-database
guidance.

## Commands

| Command | Scope | Failure behavior |
| --- | --- | --- |
| `npm run diagnostics:fast` | TypeScript, ESLint, Angular templates, backoffice module structure, and internal documentation links | Runs every check and fails if any TypeScript error, ESLint warning/error, module violation, or broken internal link remains. |
| `npm run diagnostics:sonar` | Full SonarQube analysis and server result retrieval | Fails for infrastructure, authentication, scanner, processing, timeout, API, quality-gate, issue, or hotspot failures. |
| `npm run diagnostics` | Fast and SonarQube layers | Runs both layers, summarizes failed analyzers, and never silently skips SonarQube. |
| `npm run sonar:start` | Optional `diagnostics` Compose profile | Starts only SonarQube in the `process-management-system` Compose project, waits for readiness, and bootstraps local credentials when required. |
| `npm run sonar:status` | Local server health | Displays the exact Compose service and server status. |
| `npm run sonar:stop` | Local server lifecycle | Stops only SonarQube and preserves its named data, extension, and log volumes. |
| `npm run test:diagnostics:fast` | Local analyzer regression fixtures | Proves warning/error/type/root/test/uncommitted-file coverage, removes fixtures, and reruns a clean fast scan. |
| `npm run test:diagnostics:sonar` | Live server regression fixtures | Proves server/auth/scanner failures, Docker and independent TypeScript rules, then performs a clean rescan. |

`npm run diagnostics:local` remains an alias for `diagnostics:fast`; it does not claim SonarQube
coverage.

## Local SonarQube setup

1. Start Docker Desktop.
2. Run `npm run sonar:start`.
3. Run `npm run diagnostics:sonar` once to create the `process-management-system` project.
4. In VS Code, open the SonarQube Connected Mode view and connect to `http://localhost:9000`.
5. Use project key `process-management-system`. The checked-in `.sonarlint/connectedMode.json`
   records the same association for the workspace.

The service appears as `process-management-system-sonarqube-1` under the main Compose project. It
does not start during normal `docker compose up` because it belongs to the optional `diagnostics`
profile.

## Credentials and secrets

For local development, `sonar:start` changes the default local administrator password, generates a
user token, and writes these two files:

- `.sonarqube/admin-password`
- `.sonarqube/token`

The directory is Git-ignored. On POSIX systems the files are created with mode `0600`; on Windows,
access follows the current user's workspace permissions. The scanner reads the token file without
printing it. Only the explicit `npm run sonar:token` command prints the token so it can be entered
into the VS Code connection UI.

These credentials intentionally do **not** live in the root `.env`. That file configures the
application and is loaded by application Compose services, so placing an unrelated administrator
password or analysis token there would expose it to more processes than necessary. Separation also
prevents an application configuration dump from leaking analysis credentials.

Use the following hierarchy:

1. CI or shared environments: store `SONAR_TOKEN` in the CI platform's encrypted secret store.
2. Manual overrides: set `SONAR_TOKEN` only in the invoking process environment.
3. Local default: use the ignored `.sonarqube/token` file generated by `sonar:start`.

`SONAR_ADMIN_PASSWORD` is only a local bootstrap/recovery override and should not be committed or
placed in the application `.env`. To rotate the generated local token, revoke it in SonarQube or
remove only `.sonarqube/token`, then run `npm run sonar:start`; the stored local administrator
credential generates a replacement. Treat both files as secrets even though the server is local.

## Coverage matrix

| Files/language | Fast analyzer | SonarQube analyzer | Notes |
| --- | --- | --- | --- |
| Root scripts, Playwright, and e2e TypeScript/JavaScript | ESLint and root `tsc` | JavaScript/TypeScript | Includes saved, tracked working-tree changes. |
| API source, seeds, tests, scripts, and configs | ESLint and API `tsc` | JavaScript/TypeScript | ESLint warnings fail through `--max-warnings=0`. |
| Public and backoffice TypeScript and tests | ESLint and app/spec `tsc` configs | TypeScript | Contract-generated files remain typechecked; generated ownership stays with OpenAPI. |
| Angular component templates | angular-eslint template rules | HTML | Inline and external templates are included. |
| CSS and SCSS | — | CSS | SonarQube supplies the project-wide CSS layer. |
| Dockerfiles and Compose/YAML | — | Docker and YAML | Includes all application Dockerfiles; regression coverage proves `docker:S6471`. |
| JSON configuration/contracts | — | JSON | Dependency/build output directories are excluded. |
| Markdown project documentation | Internal link checker | Text/secrets where supported | Vendored agent-skill documentation is outside the project-doc link scope. |

The SonarQube scan excludes dependency/build/report output and the repository-managed agent skill
directories (`.agents`, `.claude`, `.devin`, and `.windsurf`). Those files are tool distributions,
not product source. Tests are indexed as tests rather than production sources. Non-ignored newly
created files are analyzed; the Sonar regression fixture explicitly disables SCM exclusions to
prove ignored, uncommitted fixture coverage.

## Why VS Code and CLI differed

- SonarQube for IDE standalone analysis is editor-triggered and does not constitute a complete
  repository scan.
- ESLint previously did not cover every root script/configuration or fail consistently on warnings.
- TypeScript must run each application and test configuration; one root compilation cannot model
  all Angular and NestJS projects.
- ESLint/SonarJS does not implement the complete SonarQube rule set and cannot analyze Dockerfiles.
- A quality gate can remain `OK` while unresolved issues exist, so the CLI also queries issues and
  hotspots through the server API after compute-engine completion.

## Known differences and troubleshooting

Connected Mode synchronizes the project association, server quality profiles, rule parameters, and
server-managed exclusions. It does not make editor-triggered analysis and full scanner analysis the
same execution model, and IDE/scanner releases may bundle different analyzer versions. TypeScript's
editor language service can also show suggestions that `tsc` does not classify as compiler errors.

For the closest supported alignment:

- use the workspace TypeScript and ESLint dependencies;
- keep the configured ESLint working directories in `.vscode/settings.json`;
- connect VS Code to the same server and project key;
- save the file before comparing it with CLI output;
- run `npm run diagnostics`, not only the fast alias, before handoff.

Failure prefixes identify the layer: `[sonar][infrastructure]`, `[authentication]`, `[scanner]`,
`[analysis]`, `[timeout]`, `[api]`, or `[configuration]`. A server that is down, an invalid token,
an incomplete scanner report, a failed compute task, or an API error always returns nonzero and is
never described as zero issues.
